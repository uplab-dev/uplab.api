# Тесты модуля uplab.api

Два независимых набора:

- **Юнит-тесты** (`Unit/`) — логика модуля, запускаются локально **без ядра Bitrix**
  и без сайта.
- **Коллекция запросов** ко всем эндпоинтам с авто-проверками — для Postman и
  Insomnia, требует развёрнутого сайта.

## Юнит-тесты (dev, локально)

```bash
composer install   # PHPUnit ставится как dev-зависимость
composer test      # то же, что vendor/bin/phpunit
vendor/bin/phpunit --filter IblockPropertyResolverTest   # один класс
```

Файлы:

- `bootstrap.php` — заглушки Bitrix, нужные только для загрузки классов
  (`Loader`, `Loc`, `CIBlockRights::PUBLIC_READ`, константа `LANGUAGE_ID`).
  К базе не обращаются;
- `Unit/Iblock/FakeIblockProperty.php` — тестовый дублёр `IblockProperty`:
  подменяет обёртки над API Bitrix готовыми строками выборки и пишет журнал
  вызовов. Логика класса не переопределяется;
- `Unit/Iblock/IblockPropertyFilterTest.php` — базовый (защитный) фильтр и
  фильтр запроса;
- `Unit/Iblock/IblockPropertyResolverTest.php` — карта «тип свойства →
  резолвер», расширение карты наследником, ошибки резолвера;
- `Unit/Iblock/IblockPropertyValuesTest.php` — сборка значений по каждому типу
  свойства;
- `Unit/Iblock/IblockPropertyOverridesTest.php` — точечная правка сортировки,
  формата и фильтра для конкретного свойства конкретного инфоблока;
- `Unit/Iblock/ProjectCustomTypeExampleTest.php` — живой пример проектного
  расширения: типы `SASDCheckboxNum` / `SASDSection` модуля `asd.iblock`,
  которые сам `uplab.api` не поддерживает. Тот же класс приведён в README —
  если пример разойдётся с кодом модуля, тест упадёт.

Как добавлять тесты на новую логику: запрос к Bitrix держите в отдельной
тонкой обёртке (как `fetchPropertyValueRows()` и другие в блоке «Обращения к
API Битрикс»), а преобразование данных — в отдельном методе. Тогда тест
наследует класс, подменяет обёртку массивом-фикстурой и проверяет чистую
логику. Прод-зависимостей это не добавляет: PHPUnit и автозагрузка тестов
объявлены в `require-dev` / `autoload-dev`, на сервер (`composer install
--no-dev`) не попадают.

## Файлы коллекции

- `uplab.api.postman_collection.json` — коллекция (Postman v2.1).
- `uplab.api.postman_environment.json` — шаблон окружения (переменные).

## Импорт

### Postman
1. **Import** → перетащите оба файла.
2. Выберите окружение **«uplab.api — окружение (шаблон)»** (справа вверху).
3. Отредактируйте переменные под свой проект (см. ниже).

### Insomnia
1. **Import** → выберите `uplab.api.postman_collection.json` (Insomnia понимает
   формат Postman v2.1).
2. Переменные лежат в самой коллекции (Postman variables) — при необходимости
   задайте их в Insomnia через Environment.

## Переменные

| Переменная | Что это | Пример |
|---|---|---|
| `baseUrl` | Домен сайта без завершающего `/` | `https://my-site.ru` |
| `siteId` | ID сайта (модуль трактует его как язык, напр. `ru`) | `ru` |
| `iblockCode` | Символьный код инфоблока | `catalog` |
| `elementCode` / `elementId` | Код / ID элемента | `phone-x`, `123` |
| `sectionCode` / `sectionId` | Код / ID раздела | `smartphones`, `45` |
| `hlblockCode` | Имя (NAME) highload-блока | `Vendors` |
| `pageCode` | Код статической страницы (ИБ `pages`) | `about` |
| `formCode` | Символьный код (SID) веб-формы | `FEEDBACK` |
| `contentPageCode` | `UF_PAGE` контента | `main` |
| `contentElementId` | ID записи контента (для bulk/delete) | `10` |
| `menuCode` | Код инфоблока меню | `top` |
| `searchQuery` | Поисковый запрос для `/api/search` | `test` |
| `bitrixSessid` | CSRF-токен (`BX.bitrix_sessid()`), нужен для content-мутаций | |

> **Важно:** для детальных эндпоинтов (`elementCode`/`elementId`, `sectionCode`/`sectionId`, `pageCode`, `formCode`, `menuCode`, коды инфоблоков) переменные должны указывать на **реально существующие** записи вашего сайта. Их happy-path тесты проверяют строго `200` — если пришёл `404`, значит переменная указывает на несуществующую запись (тест намеренно падает, чтобы это подсветить). Сценарии «не найдено» вынесены в отдельные запросы и проверяют `404` осознанно.

## Запуск

- Одиночный запрос — кнопка **Send**; результаты проверок — вкладка **Test Results**.
- Все сразу — **Runner** (Postman) по коллекции.

## Что проверяется

Для **каждого** запроса (на уровне коллекции):
- нет ответа `5xx` (ловит фатальные ошибки);
- тело — валидный JSON;
- в теле нет утечки PHP-ошибки/трейса.

В отдельных запросах — ожидаемый статус и поведение, в т.ч. регрессы, закрытые
в 1.8.0:
- раздел по id с **символьным** кодом инфоблока — не 500;
- список элементов HL с множественными полями-привязками — не 500;
- поиск с **пустым телом** — не 500; `limit=0` отклоняется с `400`;
- content `bulk`/`delete` **без `sessid`** — отказ (CSRF).

в 1.12.0:
- `filter` с управляющими ключами (`LOGIC`, `PERMISSIONS_BY`, `SHOW_HISTORY`, `SHOW_NEW`) — выборка не расширяется: `meta.total` совпадает с запросом без фильтра, элементы только из запрошенного инфоблока;
- `limit` выше максимума — `400`; фильтр по 200 ID — `200` (лимит сложности не срабатывает);
- сортировка `ASC,NULLS` принимается.
- `Content-Type: application/json` с битым телом — `400`; отправка веб-формы с `x-www-form-urlencoded` продолжает работать (не `400`).

## Content-эндпоинты (нужна авторизация)

`GET/POST /api/content/admin/*` и `/api/content/bulk` требуют **авторизованного
пользователя Bitrix** с правами на HL-блок. Их «положительные» тесты проверяют
не только HTTP-код, но и **тело** (`status !== "error"`), т.к. при отказе доступа
модуль отдаёт `HTTP 200` + `{ "status": "error", ... }`. Поэтому:

- запускать их нужно с **сессией администратора** (cookie авторизации) и заполненным
  `bitrixSessid`;
- **без авторизации эти тесты намеренно падают** (`status:error «Доступ запрещён»`) —
  это правильный сигнал, а не ложная ошибка;
- тесты «**без sessid**» — наоборот, зелёные, когда доступ корректно **отклонён**
  (проверка CSRF).

## Highload-эндпоинты (права на блоке)

По умолчанию `/api/hlblock/*` публичны и happy-path проверки проходят анонимно. Если на
HL-блоке выдано право `hl_element_read` (вкладка «Права доступа»), блок становится закрытым:
корректный ответ для чужой сессии — `403`, а happy-path нужно запускать с подходящей
сессией или выдать право тестовой группе.

## Важно

- Запрос **«Delete С sessid»** реально удаляет запись контента при валидных
  `sessid` и правах. Запускайте осознанно (лучше на тестовых данных).
- Проверки статусов рассчитаны на дефолтный формат ответа модуля. Если у вас
  переопределён контроллер/формат — подправьте ассерты под себя.
- `bitrixSessid` можно взять в консоли браузера на странице админки:
  `BX.bitrix_sessid()`.
